# 站内通知

站内通知让服务端把与用户本人有关的事件 (举报结果、账号安全、系统消息) 和全局公告告诉用户。
本文说明客户端如何组织这些通知，以及几条代码里看不出来的约定。

## 分类与类型

服务端为每条通知记录一个细分的类型，并按“谁在和我说话”为类型分配一个分类。每个分类是通知中心的一个标签页（客户端称为分组）。
标签页按下表的顺序排列，默认选中“通知”：

| 标签页 | 分类            | 已知类型                                           | 本版本客户端的展示 |
|-----|---------------|------------------------------------------------|-----------|
| 互动  | `interaction` | `comment_reply`、`mention`、`reaction`、`follow` | 通用展示      |
| 通知  | `notice`      | `system`、`report_result`、`account_security`    | 各类型自己的展示  |

私信 (`direct_message`) 有自己的分类，本版本客户端没有它的标签页，所以不请求它。

公告不属于任何分类。它是管理员发布的全局内容，所有人（包括游客）都能看到，有单独的列表，已读状态也单独记录。

类型属于哪个分类由服务端决定，客户端不保存这张表：列表、未读数和“全部标为已读”都按分类请求。
两个标签页都请求自己的分类，有各自的未读数、下拉刷新和“全部标为已读”。
游客在两个标签页上都看到登录提示。只有一个标签页时，通知中心不显示标签栏。

系统消息 (`system`) 可以带一个事件。客户端认识的事件（目前只有 Bangumi 授权过期）使用客户端自己的文案和操作；
没有事件或不认识的事件显示通用展示内容（见“向前兼容”）。

## 通知中心的布局

顶栏下依次是公告入口、标签栏和当前标签页的列表。公告入口和标签栏固定不动，只有列表滚动。

每个标签页有自己的列表、滚动位置、下拉刷新和本地已读状态。点击标签或左右滑动切换标签页；
滑动只响应触摸，鼠标拖动不翻页，与 App 中其他带标签的分页一致。切换标签页不会重新加载列表。

标签文字后的数字是这个标签页对应分类的未读数，没有未读时不显示；读屏读作“N 条未读”，而不是徽标上的数字。
头像红点依据的未读通知数是各标签页未读数之和。顶栏的“全部标为已读”只作用于当前标签页。

列表为空时，列表可见区域的中央显示空状态：图标、标题和一句说明这个列表会显示什么的文字。
空状态是列表中的一项，所以空列表同样可以下拉刷新；可见区域放不下时它从列表顶部开始，随列表滚动。
公告列表为空、宽屏中尚未选择通知或公告、单独的详情页找不到通知或公告时，使用同样的样式。宽屏中列表为空时没有可选的内容，详情栏留空。
加载失败和游客的登录提示使用 App 通用的错误卡片。

## 点击去向

| 类型                 | 点击行                     | 行内操作              |
|--------------------|-------------------------|-------------------|
| `report_result`    | 举报结果详情                  | 无                 |
| `system`           | 系统消息详情                  | Bangumi 授权过期：重新授权 |
| `account_security` | 账号设置（窄屏和宽屏都跳转，不在右侧显示详情） | 无                 |
| 其他类型               | 通用详情                    | 无                 |

账号安全通知没有详情页：它只是提醒用户去检查账号，相关的操作都在账号设置中。

举报结果详情有一个按钮，跳转到被举报评论所在的剧集、条目、人物或角色；缺少对应的 ID 时没有这个按钮。
被举报评论的类型客户端不认识时，按钮前往通用展示内容中的位置，没有位置时同样没有按钮。
单独的详情页中它是内容底部的文字按钮。宽屏双栏中详情栏与列表并排时，它是详情栏顶栏右侧的图标按钮，内容底部没有这个按钮；
窗口变窄、只显示详情栏时，与单独的详情页一样在底部。

有行内操作的行在两行文字下方多一行文字按钮，整行改为顶部对齐；按钮向左偏移自身的内边距，让按钮文字与上方文字对齐。
点击行内操作和点击行一样会把通知标为已读，但只执行按钮的操作，不打开详情。

通用详情用于客户端没有专门展示方式的类型，只显示通用展示内容：左侧是图标或图片，右侧依次是标题上方的一行、标题和时间，
下面是正文（与系统消息一样可以选择复制，其中的网址可以点击）。通知带有客户端支持的位置时，正文下方有一个前往按钮，
按钮文字说明去哪里，例如“前往该剧集”；网页链接是带外链图标的“查看详情”，在浏览器中打开。
客户端不认识这个类型时，最下方提示当前版本可能无法完整显示这条通知，“检查更新”打开软件更新设置。

没有已知事件的系统消息同样按通用展示内容中的位置显示前往按钮。系统消息和通用详情的按钮总是在内容底部，不放到顶栏。

## 向前兼容

已发布的客户端使用生成的 API 代码，遇到不认识的枚举值会导致整个响应解析失败。因此会增加取值的字段在协议中都是字符串，
客户端自己把认识的取值映射为枚举。

通知中心要做到：服务端在已有分类中新增一种类型时，已发布的客户端不需要更新就能显示它。为此：

- 客户端按分类请求，服务端决定类型属于哪个分类，所以新类型会出现在对应标签页的列表和未读数中。
- 每条通知都带有服务端生成的通用展示内容：标题、可选的正文、标题上方的一行（例如条目与剧集）、图标、图片（例如对方的头像），
  以及点击后前往的位置（剧集、条目、人物、角色或网页链接）。客户端认识的类型用自己的本地化文案和操作，
  其他类型（包括本版本没有专门展示方式的互动类型）只用通用展示内容。
- 通用展示内容表达不了一种类型的全部信息，所以客户端显示不认识的类型时会提示用户更新：通用详情的底部有提示和“检查更新”，
  已加载的列表中有这种通知的标签页在列表顶部显示一条提示，“更新”同样打开软件更新设置。每个标签页最多一条，不逐行提示。
  认识的类型缺少自己的内容时同样只用通用展示内容显示，但更新不会让它显示得更完整，所以不提示。
- 前往的位置按剧集、条目、人物、角色、网页的顺序取客户端支持的第一个；网页只接受 http(s) 链接，在浏览器中打开。
  以后增加的位置（例如某条评论）在旧版本客户端上退回到这些位置之一。
- 新增分类需要客户端增加标签页。客户端只请求自己有标签页的分类，所以在此之前这个分类的通知不会出现，也不计入红点。
- 以后可能增加取值的子类别，例如系统消息事件、账号安全事件、公告分类、第三方平台、通用展示内容的图标，同样是字符串。
  未知的系统消息事件和账号安全事件显示通用展示内容的标题和正文；未知的账号安全事件点击后同样打开账号设置。
  未知的公告分类显示为“公告”，第三方账号解绑中不认识的第三方平台显示为“第三方账号已解绑”。
- 举报结果中的举报原因和被举报评论的类型沿用举报接口的取值，但同样以字符串下发。不认识的原因显示为“其他”。
  不认识的评论类型用通用展示内容描述被举报的对象（正文的第一行，没有正文时显示为“评论”），
  跳转按钮前往通用展示内容中的位置。
- 这些不认识的子类别只影响通知的一部分，通知的类型是客户端认识的，所以不提示更新。

## 入口与红点

通知不是高频功能，所以入口不常驻在顶栏上，而是放在头像菜单里：点主页面（探索、追番、下载）顶栏的头像，菜单里有“通知”。
游客也有这一项，因为公告对所有人可见；通知中心对游客显示登录提示。TV 没有通知入口。

有未读内容时，头像右上角和菜单里的“通知”上各显示一个红点，两处总是一致。入口只用红点提示，不显示数字。

- 有未读通知时显示。未读通知只统计有标签页的分类中、没有在本机通知设置中关闭的类型。
- 没有未读通知但有未读公告时也显示。用户可以在通知设置中关闭这种情况下的红点；公告列表里的未读标记不受影响。
- 都没有时不显示。游客没有已读状态，所以不会出现红点，顶栏上的“登录”按钮也不显示红点。
  登录状态失效时（例如 token 过期且因网络错误未能刷新）顶栏同样显示“登录”按钮，此时即使还留着之前获取的未读数，两处也都不显示红点。

头像通常是照片，红点周围会从头像上挖去一圈，露出下面的顶栏背景，这样在任何头像上都能看清。
顶栏可能是毛玻璃，滚动后也会变色，所以挖空而不是描一圈固定颜色的边。

## 刷新时机

未读状态由一个全局的管理器维护。它只在用户已登录且 App 位于前台时定期轮询，避免在后台或游客状态下产生无用的请求。
另外在以下时机立即刷新：启动、新用户登录、App 回到前台、以及任何标记已读的操作之后。
游客没有未读通知，只在启动和回到前台时获取一次最新公告，用于通知中心顶部的公告入口。退出登录时立即清空未读数。

App 是否在前台由 UI 根组件的生命周期决定，因为各平台没有统一的前后台信号。
桌面端把窗口隐藏到系统托盘时生命周期不会停止，所以另外判断窗口是否可见：隐藏到托盘也算后台。
管理器初始视为后台，根组件挂载后报告的第一次前台就是启动时的刷新。TV 不挂载这个根组件，所以 TV 上不会自动请求。

刚登录时 HTTP 客户端可能还没有用上新的 token。登录后第一次以登录用户身份获取未读状态时，遇到 401 会短暂等待后重试几次。

## 通知设置

举报结果和账号安全各有一个开关，默认开启。两者与用户关心的东西不同，所以分开设置。系统消息没有开关。

开关保存在本机，不同步到服务端。关闭某类通知后，客户端请求列表、未读数和“全部标为已读”时都排除这个类型：
这类通知不在本机的通知中心显示，不计入头像和菜单上的红点，也不会被“全部标为已读”标记，重新打开后照常显示。
设置改变时，通知中心重新加载列表，未读状态也立即刷新。客户端不认识的类型没有开关，总是显示。

## 已读

打开一条通知或执行它的行内操作就会把它标为已读。列表先在本地把它显示为已读，再请求服务端，不重新加载已经分页的数据；
请求失败时撤销本地标记。每个标签页的本地标记互不影响。本地标记属于当前账号，登录状态变化时清空。

“全部标为已读”只标记当前标签页的分类中不晚于已加载的最新一条的通知。这样，用户浏览期间新到达、还没看到的通知仍然是未读的。
列表不会自动加载新通知，但未读数会定时刷新。所以标记完成后、以及某个标签页的未读数增加到超过它列表中的未读通知时，
通知中心重新加载这个标签页，让新通知显示出来；否则按钮仍然可用，用户却看不到、也清不掉这些通知。
列表默认让原来的第一项保持在原处，插在最前面的通知会在视口上方，所以列表停在顶部时，重新加载后仍停在顶部；
用户已经向下滚动时，位置不变。

公告进入列表即已读，公告列表没有“全部标为已读”按钮。服务端按“已读水位 + 单独已读的公告”计算公告的已读状态：
登录用户的公告列表每加载完一页，客户端就把水位移到已加载的最新一条公告的发布时间，然后刷新未读状态，
所以离开列表后通知中心里公告入口的红点就消失了。之后发布、用户还没看到的公告仍是未读。

列表本身仍显示进入前的未读标记，让用户看出哪些是新的：每条公告保持本次浏览中第一次加载到它时服务端给出的已读状态，下拉刷新也不变。
之后才加载的页同样显示加载时服务端的状态，所以发布时间不晚于水位的公告这时已经是已读。
置顶公告排在前面，后面的页里可能出现比水位更新的公告；它们显示为未读，加载后水位继续前移。
标记失败时，下次加载（例如下拉刷新）会重试。点击一条公告只在本地把它显示为已读，水位已经覆盖它时不再单独请求。

游客没有已读状态，公告列表对游客不显示未读标记，也不标记已读。

## 文案

通知列表的每一行有两行文字：第一行说明发生了什么，第二行说明对象或细节，例如“你举报的评论已被处理”和“葬送的芙莉莲 第 12 话”。
有行内操作时，按钮在第三行。

通用展示内容带有标题上方的一行时，列表行是三行项：第一行是对象（例如“葬送的芙莉莲 第 1 话”），第二行说明谁做了什么，
第三行是内容预览。时间和未读标记随之移到第一行。三行项与有行内操作的行一样顶部对齐。
左侧有图片（例如对方的头像）时显示为圆形图片，图片加载完成前和加载失败时显示图标；图标不认识或没有时使用通用的通知图标。

- 各部分分开显示，不用“·”拼接成一行。
- 客户端自己的文案不引用用户自己写的评论内容，被举报评论的快照只在举报结果详情中显示。通用展示内容的文字由服务端提供，原样显示。
- 条目名遵循用户的“显示原名”设置。
- 通知列表中的时间与标题在同一行，要尽量短，以免挤掉标题：今天的通知显示相对时间，更早的只显示“昨天”或日期，不是今年的才带年份。
- 公告列表只显示发布日期，不使用相对时间，同样只有不是今年的才带年份。
- 详情中的时间（通知和公告的时间、举报和处理的时间、被举报评论的发表时间）显示日期和精确到分钟的时间，
  例如“10 月 11 日 19:02”；不是今年的带年份，例如“2025 年 10 月 11 日 19:02”。
