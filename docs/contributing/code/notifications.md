# 站内通知

站内通知让服务端把与用户本人有关的事件 (举报结果、账号安全、系统消息) 和全局公告告诉用户。
本文说明客户端如何组织这些通知，以及几条代码里看不出来的约定。

## 分组与类型

服务端为每条通知记录一个细分的类型。客户端按“谁在和我说话”把类型归入分组，每个分组是通知中心的一个标签页：

| 分组 | 类型                                                   | 状态     |
|----|------------------------------------------------------|--------|
| 通知 | `system`、`report_result`、`account_security`          | 已实现    |
| 互动 | `comment_reply`、`mention`、`reaction`、`follow`        | 预留，不产生 |
| 私信 | `direct_message`                                     | 预留，不产生 |

公告不属于任何分组。它是管理员发布的全局内容，所有人（包括游客）都能看到，有单独的列表，已读状态也单独记录。

只有一个分组时，通知中心不显示标签页。预留的分组不在客户端支持的分组中，所以不显示对应的标签页，也不请求这些类型。

## 向前兼容

已发布的客户端使用生成的 API 代码，遇到不认识的枚举值会导致整个响应解析失败。因此：

- 列表和未读数接口总是带上客户端能渲染的类型。服务端只返回、只统计这些类型，
  所以服务端新增类型后，旧版本客户端既看不到这些通知，也不会因为它们显示红点。
- 以后可能增加取值的子类别，例如账号安全事件、公告分类、登录方式、第三方平台，在协议中是字符串而不是枚举。
  客户端把不认识的值映射为通用的展示：未知的账号安全事件显示为“账号安全提醒”，未知的公告分类显示为“公告”。
  新设备登录中的平台由服务端下发，客户端只显示认识的平台名，不认识的平台不显示。
  第三方账号解绑中不认识的第三方平台显示为“第三方账号已解绑”，详情不显示平台。
- 举报结果中的举报原因和被举报评论的类型沿用举报接口的取值，但同样以字符串下发。
  不认识的原因显示为“其他”；不认识的评论类型显示为“评论”，并且不提供跳转，因为客户端不知道它的哪些字段描述了被举报的对象。

## 入口与红点

通知不是高频功能，所以入口不常驻在顶栏上，而是放在头像菜单里：点主页面（探索、追番、下载）顶栏的头像，菜单里有“通知”。
游客也有这一项，因为公告对所有人可见；通知中心对游客显示登录提示。TV 没有通知入口。

有未读内容时，头像右上角和菜单里的“通知”上各显示一个红点，两处总是一致。入口只用红点提示，不显示数字。

- 有未读通知时显示。未读通知只统计客户端能渲染的类型。
- 没有未读通知但有未读公告时也显示。用户可以在通知设置中关闭这种情况下的红点；公告列表里的未读标记不受影响。
- 都没有时不显示。游客没有已读状态，所以不会出现红点，顶栏上的“登录”按钮也不显示红点。
  登录状态失效时（例如 token 过期且因网络错误未能刷新）顶栏同样显示“登录”按钮，此时即使还留着之前获取的未读数，两处也都不显示红点。

头像通常是照片，红点周围会从头像上挖去一圈，露出下面的顶栏背景，这样在任何头像上都能看清。
顶栏可能是毛玻璃，滚动后也会变色，所以挖空而不是描一圈固定颜色的边。

## 刷新时机

未读状态由一个全局的管理器维护。它只在用户已登录且 App 位于前台时定期轮询，避免在后台或游客状态下产生无用的请求。
另外在以下时机立即刷新：启动、新用户登录、App 回到前台、以及任何标记已读的操作之后。
游客没有未读通知，只在启动和回到前台时获取一次最新公告，用于通知中心顶部的公告入口。退出登录时立即清空未读数。

App 是否在前台由 UI 根组件的生命周期决定，因为各平台没有统一的前后台信号。
桌面端把窗口隐藏到系统托盘时生命周期不会停止，所以另外判断窗口是否可见：隐藏到托盘也算后台。
管理器初始视为后台，根组件挂载后报告的第一次前台就是启动时的刷新。TV 不挂载这个根组件，所以 TV 上不会自动请求。

刚登录时 HTTP 客户端可能还没有用上新的 token。登录后第一次以登录用户身份获取未读状态时，遇到 401 会短暂等待后重试几次。

## 已读

打开一条通知或公告就会把它标为已读。列表先在本地把它显示为已读，再请求服务端，不重新加载已经分页的数据；请求失败时撤销本地标记。
本地标记属于当前账号，登录状态变化时清空。

“全部标为已读”只标记不晚于列表中已加载的最新一条的通知。这样，用户浏览期间新到达、还没看到的通知仍然是未读的。
列表不会自动加载新通知，但未读数会定时刷新。所以标记完成后、以及未读数增加到超过列表中的未读通知时，通知中心重新加载列表，
让新通知显示出来；否则按钮仍然可用，用户却看不到、也清不掉这些通知。

公告的已读状态由服务端按“已读水位 + 单独已读的公告”计算：全部标为已读把水位移到已加载的最新一条公告的发布时间，之后发布、用户还没看到的公告仍是未读。游客没有已读状态，公告列表对游客不显示未读标记。

## 文案

通知列表的每一行有两行文字：第一行说明发生了什么，第二行说明对象或细节，例如“你举报的评论已处理”和“葬送的芙莉莲 第 12 话”。

- 两部分分开显示，不用“·”拼接成一行。
- 列表中不引用用户自己写的评论内容。被举报评论的快照只在举报结果详情中显示。
- 条目名遵循用户的“显示原名”设置。
- 列表中的时间与标题在同一行，要尽量短，以免挤掉标题：今天的通知显示相对时间，更早的只显示“昨天”或日期，不是今年的才带年份。
  详情中显示完整的日期和时间。
