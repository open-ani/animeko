# 选源界面

播放页与批量下载里供用户查看候选资源、切换数据源、手动选定资源的界面。本文说明模式划分、容器版式与手动查找的记忆机制背后的取舍。
过滤、排序与自动选择的算法见 [MediaSelector](media-selector.md)，数据源的浏览协议见
[MediaSource](media-source.md#列表模式与自动匹配)，文件索引见[代码地图](media-code-map.md#选源界面)。

## 三种模式

选择器有三种模式，由顶栏右侧的下拉切换：

- **自动匹配**：列出会话里的 WEB 数据源及其线路，资源由自动选择决定，用户只在需要时点某条线路换源。
  绝大多数用户只用这一页，因此它是默认模式。
- **手动查找**：绕过自动匹配，直接浏览某个数据源的条目、线路与剧集，由用户指定哪一项对应正在观看的剧集。
- **BT 资源**：BT 候选的高密度列表，带按集、按源与按偏好的筛选。BT 用户是少数，这一项排在菜单末尾；
  会话里没有 BT 数据源（例如 iOS 不创建 BT 源）时不出现。

模式是展示状态，与设置里的资源类型偏好 `preferKind` 无关：切模式不改设置，不改正在播放的内容，也不持久化；
它在播放页会话内保持，离开播放页即丢失。默认模式由偏好推导：偏好 BT 且会话里有 BT 源时落在 BT 页，
其余情况（偏好 WEB、无偏好、没有 BT 源）都落在自动匹配。「会话里有 BT 源」按会话的数据源结果判定而不是判断平台，
这样 iOS 与「用户禁用了全部 BT 源」走同一条路。

数据源结果是异步就绪的，默认模式会在打开后翻转。宿主在打开选择器时锁存一次默认模式，之后的翻转对已打开的容器无效，
避免用户正在看自动匹配页时页面跳到 BT。页面仍在加载时打开则不锁存，由容器响应翻转。

## 自动匹配页

自动匹配页只有数据源与线路，没有分辨率 / 字幕 / 字幕组筛选：Selector 数据源产出的 WEB 资源在这些属性上近乎常量
（分辨率恒为配置默认值、字幕语言恒有值），筛选没有信息量，反而让用户误以为可以靠它换到别的资源。
数据源行的顺序沿用数据源结果列表的静态阶级排序，禁用的源排在最后。验证码、限流与失败直接显示在源行上，
处理方式见 [Web 数据源验证码处理](web-captcha.md)。

正常的源行之后、查询失败的源行之前有一个「找不到想看的？手动查找」文字按钮，点击切到手动查找。它是救援入口：WEB 源全部选不出资源时，
自动选择退到 BT 的兜底依赖时序，并不可靠；名字不含集号的 OVA、特典更是任何自动匹配规则都选不出来。
手动查找是这两种情况下确定的出路。多数用户用不到它，所以只是一个不抢眼的文字按钮，不做成卡片。它排在失败的源前面：失败行帮不上忙，
放在按钮前面只会把救援入口挤到列表最后，而源纷纷失败时恰恰最需要它。验证码与限流不算失败，
用户处理后仍会出结果，照常排在按钮前面。

## 手动查找

手动查找建立在数据源的[浏览协议](media-source.md#列表模式与自动匹配)上：搜索条目、打开条目得到线路与剧集、
把选中的一集转换成资源。页面把浏览结果原样列出，不做匹配、不排序、不过滤，由用户判断哪一条对应正在观看的剧集，
这正是浏览协议存在的意义。

源列表只包含声明了支持浏览的已启用数据源，按数据源管理器的实例顺序排列。接口上的浏览方法有默认实现，
运行时无法区分「支持但没搜到」与「不支持」，因此需要数据源显式声明。自动匹配被关闭（`autoMatch.enabled = false`）
的源查询时不发请求，在自动匹配页永远是空结果，但在手动查找里照常可用。默认选中的源依次取：
本条目浏览记忆所记的源、本条目记忆的 Web 源、列表第一个。默认关键字是条目名。

打开页面与换源时自动用当前关键字搜索当前源：默认关键字多数时候就是对的，让用户再点一次搜索是多余的一步。
搜索结果按源缓存，用户在几个源之间来回比较时，切回已用同一关键字搜过的源直接显示结果，不重复请求；
切走时原来那个源的搜索不取消，结果照常进缓存。关键字变了（提交了新词，或输入框里是新词）再切回来会按新词重搜。
失败的结果同样缓存，只在用户点重试时重搜：被验证码挡住的源若每次切回来都重搜，会反复弹出验证。
提交关键字总是重新搜索当前源，即使关键字没变，可以当作刷新。

线路以它在浏览结果中的位置区分，而不是名字：站点上线路名可以重复，也可以没有线路概念。
剧集网格默认预选集号与当前集相同的一项。

浏览请求与自动匹配的查询走同一条页面获取链路，同样会被验证码或限流挡住。被验证码挡住时页面直接呈现交互式验证，
解决后重试一次同一请求；平台没有浏览器（iOS）时显示不支持的提示，不提供重试。其余失败显示错误与重试。

点击网格里的一集直接播放，不再确认。网格头部右侧是「记住选择」开关，默认开，它决定这次点选的影响范围：

- **开**：正式选择。它把线路名与数据源写入本条目的四维偏好、把该源记为本条目的记忆 Web 源，
  并写入浏览记忆（见下节），之后每一集自动选择记住线路里对应位置的一项。
- **关**：临时选择。只对本集有效，不写任何偏好与记忆；下一集照常自动匹配。

绝大多数用户手动找到一部作品后都希望之后按同一条线路往下看，所以记住是默认行为；
开关放在点选的位置，用户在做决定之前就能看到这次会被记住，也能就地关掉。每次点选都弹确认只是多一步，
误点的代价却很小：再点一次正确的集，播放与记忆一起改正。开关状态是全局设置，关过一次的用户不必每次再关；
在某个条目上关掉时，顺带删除这个条目已有的记忆，否则下一集仍会按旧记忆回放。

两条路径都把当前集的集号交给数据源生成资源，这样资源带有当前集的剧集范围，能通过选择器的按集过滤，
在界面里也显示为当前集。

批量下载对话框里点选的一集是这一集要下载的资源，与在自动匹配页点选一条线路相同：交给下载会话，
由会话保存偏好并进入选集。条目的其他集按与浏览记忆回放相同的位置规则（见下节）在同一线路里取对应的一项，
一并交给会话，选集时可以勾选：手动查找到的线路通常不在自动匹配的候选里，不这样做就只能下载这一集。
同一集在自动匹配的候选里也有同线路的单集资源时，用按位置取的那一项，理由与回放不看站点集号相同。
这里没有「记住选择」开关，也不写浏览记忆：浏览记忆服务于播放时的切集回放，
用户在下载弹窗里只是挑下载资源，不应因此改变之后播放时的选择。

播放页手动查找的状态（搜索结果、打开的条目、选中的线路与剧集）由 ViewModel 持有一份，三个宿主共用，
从详情页进入全屏播放器不丢失。批量下载对话框的状态属于这一集的选源：在选源与选集之间来回、
隐藏后重新打开弹窗都保留，换到别的集或会话结束后丢弃。

## 浏览记忆

开着「记住选择」点选剧集时，按条目记录：数据源、条目（浏览结果里的条目引用，跨浏览稳定）、线路的位置与标识、
剧集在线路中的位置，以及当时把它当作条目的第几集播放。切集时，播放页在自动选择之前先按记忆回放：
浏览记住的条目，在记住的线路里找目标集，命中即选择，不等自动匹配的查询。

回放与自动选择在同一协程里串行：回放未命中才启动自动选择，已有选择时自动选择也不提交，因此两者不会互相覆盖。
回放整体有超时，任何失败（网络、验证码、源不可用）都视为未命中并退回自动匹配，不弹验证码。

**本地缓存优先于回放。** 自动选择把本地缓存放在最高优先级，回放不能反转它：切集时先等本会话的本地缓存源完成
（有短超时），本集已有可用缓存就跳过回放。

**只按位置找，不看站点集号。** 记忆记下「线路里第 k 项被当作第 p 集播放」。找第 t 集时取第 k + (t − p) 项，
命中即正式选择，并把记忆更新到新位置，保持链式；跳集、倒退同样按这个偏移。
用户记住选择时认定的正是这个对应关系：下一话播放下一项。
数据源解析出的集号与条目集号的对应五花八门：续季在站点上从 01 重新编号，整部 OVA 条目被列作 OVA01、OVA02 接在正片后面，
拿集号去比会命中别的项（后者会命中正片的 02），所以回放完全不用它。
t 与 p 不是同一类编号（正片与 SP）或差不是整数时推算不了，按未命中处理。
回放不校验取到的项是否真的对应目标集：记忆代表用户的判断，按偏移取就是期望的行为。
站点列表与条目剧集不一一对应（多了总集篇、缺了某一集）时取到的项会错开，由用户再点选一次纠正。

**在别处手动换源即结束记忆。** 用户在自动匹配页点了别的线路、或在 BT 页选了一条资源，说明不想再按记忆走，
这个条目的记忆随之删除，下一集回到自动匹配。否则记忆会在下一集把用户拉回原来的线路，而页面上没有任何地方说明原因。
回放自己的选择与手动查找的点选不走这条路径，不会删除记忆。

**回放的正式选择会重写四维偏好。** 正式选择与用户手动点选走同一条路，会把线路名写入本条目的字幕组偏好、
把源写入数据源偏好。WEB 资源的这些属性近乎常量，接受这个副作用。

**三条持久化通道各管一事。** 播放页有三种记忆：按条目的四维偏好（字幕组、分辨率、字幕语言、数据源）
决定自动选择在候选里挑哪一条；记忆的 Web 源决定自动选择先等哪个源、并阻塞其他网络源；
浏览记忆决定在自动匹配之前先去哪个条目的哪条线路找。浏览记忆不取代前两者：记住选择时三条都写，
回放未命中时前两条仍在自动匹配里生效。浏览记忆直接挂起写入，不经偏好保存的防抖管线，
点选后立即切集也不会丢。

**失效记忆的代价。** 条目页 404、线路被站点删除的记忆每集都会付一次条目页请求并推迟自动选择。
条目页返回空线路列表时按条目在内存里节流，十分钟内跳过请求；线路列表非空但按位置和标识都找不到线路时，
记忆已结构性失效，直接删除。剧集不存在、网络错误、超时都保留记忆。

播放页的查询会话重建（例如网络错误后重试）会重新触发回放，再付一次条目页请求；
临时选择随选择器丢失，由这次回放重新建立。

## BT 资源页

BT 候选与 WEB 不同：同一集有几十条来自不同字幕组、分辨率、字幕形式的资源，用户需要对比属性才能挑选。
因此它是独立的高密度页面，不与自动匹配页混排；行内不显示数据源名，数据源由筛选行的下拉切换。
列表包含 BT 与本地缓存两种类型的候选，缓存项标出「已缓存」。

筛选行的三个控件对应三个不同层次的状态：

- **「第 N 话」**：是否应用选择器的第 0 条规则。开启时列表基于按当前集筛选后的候选；关闭时基于不筛选剧集的条目级候选。
  关闭是为了合集与集号解析失败的资源：它们在按集筛选下以「集数不符」被排除。
- **数据源下拉**：纯界面过滤，按数据源 id 隐藏其他源的行，不写偏好；面板里的计数与源状态（查询中、失败、禁用）
  来自会话的数据源结果。写偏好会让下一集的自动选择只看这个源，与用户「先看看某个源有什么」的意图不符。
- **筛选面板**（分辨率 / 字幕 / 字幕组）：会话偏好，与自动选择使用同一份四维偏好。「重置」把三项都置为「显式无值」
  并写入本条目偏好，效果是本会话不按该维度筛选、同时屏蔽全局默认值；它不是「回到全局默认」。

四维偏好不是 BT 专用的：选中一条 WEB 资源会把线路名写进字幕组偏好、把 WEB 源写进数据源偏好。原样套到 BT 候选上，
字幕组「线路 1」一条都匹配不到，整页都成了「低于偏好」。因此 BT 页只让出现在 BT 候选里的偏好值生效，
其余视为未设置，筛选控件也按此显示；数据源偏好在 BT 页完全不生效，源维度只由数据源下拉表达，
否则它会在页面上没有任何控件的情况下隐藏其他源的行。偏好本身不改，回到自动匹配时照常生效。

「第 N 话」与数据源过滤由 ViewModel 持有，查询会话重建时保留；「显示已被排除的 N 条」的展开是一次性的，
只在本次打开期间有效。已排除列表包含选择器排除的资源（含集数不符）与「低于偏好」的资源（通过过滤但被四维偏好挡掉），
每行标一个原因。

搜索框提交新关键字会重建查询请求，全部数据源（含 WEB）重新查询，自动匹配页的列表随之重载。
查询会话按请求组织，没有按资源类型重启的入口。

点击一行是正式选择，写四维偏好。宽容器用表格（列：字幕组、标题、分辨率、字幕、大小、发布），
窄容器用紧凑列表；分界由容器宽度决定而不是窗口宽度，因此侧边栏与批量下载的底部弹窗用紧凑列表。
两种版式都完整显示标题、按宽度换行：集号、版本、合集范围与封装格式往往只写在标题里，截断后用户无从判断。

## 宿主与容器

三处宿主共用同一套页面，只负责容器：

- **详情页，窗口宽度 ≥ 600dp**：侧边栏（300–400dp）装全部三种模式，BT 页在这个宽度下是紧凑列表。
  切模式只换侧边栏的内容，不换容器：用户在侧边栏里切到 BT，预期的是侧边栏换一页，而不是侧边栏消失、弹出一个对话框。
  侧边栏太矮时例外，见下。
- **详情页，窄窗口**：底部弹窗，标题行「数据源」+ 模式下拉，三种模式都在弹窗内。
- **播放器**：与详情页一样，侧边栏装全部三种模式。
- **批量下载对话框**：底部弹窗，标题行「数据源」+ 模式下拉，三种模式都在弹窗内；会话里有 BT 源时默认 BT。
  弹窗宽度不超过 640dp，手动查找总是堆叠两页。
  资源选定后的选集步骤见[下载管理](media-downloads.md#添加下载)。

侧边栏可用高度不足 480dp 时（手机横屏：播放器侧边栏与视频区同高，详情页侧边栏与窗口同高），
除去标题、搜索框与筛选行后手动查找与 BT 的列表只剩一两行，这两种模式改为关闭侧边栏、打开容器；自动匹配的源行矮，仍在侧边栏。
关闭容器回到侧边栏并把模式置回自动匹配（模式不回去会立刻再弹容器），选中播放后全部关闭。

播放器全屏时的容器是视频区内的布局层（scrim + 面板），不是平台对话框：Android 的对话框是独立窗口，
不继承 Activity 对系统栏的隐藏，弹出即把系统栏拉回来并压缩可用高度。其余情况（非全屏的播放器、详情页）用窗口级对话框。
窗口级对话框铺满整个窗口，包括系统栏与横屏挖孔所在的边，由内容自己避开这些区域：窗口若给它们留边，
铺满的面板盖不住这几条，底下的视频和页面会从边上露出来。全屏容器的可见性与模式都由 ViewModel 持有：
容器从侧边栏页面打开，侧边栏页面关闭后容器仍要保留。

页面内部的版式只看容器宽度：≥ 720dp 时 BT 页用表格、手动查找用双栏（左栏源与结果，右栏线路与剧集），
否则 BT 用紧凑列表、手动查找堆叠为两页（先条目，后线路与剧集）。手动查找与 BT 页顶部有「正在观看 第 N 话 剧集名」提示，
自动匹配页没有：前两页让用户在整个条目的列表里挑一项，需要随时看到目标集；自动匹配页的候选本来就是按当前集筛出来的。
剧集的本季集号（EP）与序号（sort）不同时（续季接着上一季编号），提示与 BT 页的集号 chip 两个都显示，
本季集号在前、序号在括号里（「第 02 (14) 话」）：不少数据源按本季集号命名资源，用户拿来对标题的是本季集号，
只显示序号时对不上。

## 不做的事

- 不分组：分组会把要对比属性的行拆散，与高密度对比的目标相反。
- 不显示做种数、不做编码标签：资源属性里没有这些字段。
- 不持久化模式，不改 `preferKind` 的语义。
- 回放路径不弹验证码，失败即退回自动匹配。
- 界面层不解析集号，只用数据源解析的结果。
- 不自动清理失效的持久化记忆。
